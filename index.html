หา string ที่น่าสงสัย

Window → Defined Strings แล้วค้นหาคำว่า npcap จะเจอ:

C:\Windows\System32\drivers\npcap.sys
Install Network Capture Tool!

Double-click string แรก → กด Ctrl+Shift+F (Show References To) จะพาไปฟังก์ชันที่เรียกใช้ ชื่อ custom_anti_analysis_check

4

อ่าน logic (Decompile window)

เปิด Decompile panel (Window → Decompile) จะเห็นโค้ดประมาณนี้:

char * custom_anti_analysis_check(void)
{
  FILE *pFVar1;
  pFVar1 = fopen("...npcap.sys","r");
  if (pFVar1 == NULL) {
    MessageBoxA(0,"Install Network Capture Tool!",...);   // decoy #1
  } else {
    fclose(pFVar1);
    pFVar1 = fopen("...npcap.sys","r");        // เปิดไฟล์เดิมซ้ำรอบสอง!
    if (pFVar1 == NULL) {
      return "456654321234AJKP";               // ← key จริง (แทบเป็นไปไม่ได้ที่จะมาถึงตรงนี้)
    }
    fclose(pFVar1);
    MessageBoxA(0,"...Shark...",...);           // decoy #2
  }
  return "notme12345678912";
}
อ่านเกมให้ออก

โปรแกรมเปิดไฟล์เดิมสองรอบติดกัน โดยหวังว่ารอบสองจะสำเร็จเสมอ (เพราะไฟล์ยังอยู่) — ทำให้ path ที่ return key จริง แทบไม่มีทางถูก trigger ตามธรรมชาติ ต้อง บังคับให้เข้า path นั้นด้วยการ patch

Prerequisite

เงื่อนไข if (pFVar1 == NULL) แรกสุดต้องการให้ เจอไฟล์ npcap.sys จริง — เช็คก่อนว่าเครื่องคุณลง Npcap (ตัวติดตั้งมากับ Wireshark) แล้ว ด้วยคำสั่ง sc query npcap ต้องเห็น STATE: RUNNING

5

หาตำแหน่ง jump ที่ต้อง patch (Listing window)

คลิกที่บรรทัด if (pFVar1 == NULL) { return "45665..." } ใน decompile panel — Listing panel (แสดง assembly) จะกระโดดไปตำแหน่งที่ตรงกัน หา instruction:

1400014ae    74 36    JZ  0x1400014e6

นี่คือจุดตัดสินใจ: ถ้าผลลัพธ์การเปิดไฟล์รอบสองเป็น NULL (ZF=1) → กระโดดไป return key จริง เราจะบังคับให้ "กระโดดเสมอ" ไม่สนใจผลลัพธ์

6

Patch ด้วย x64dbg

  1. เปิด x64dbg → File → Open เลือกไฟล์ สำเนา ของคุณ (เช่น AntiCapture_patched.exe)
  2. กด Ctrl+G (Go to Expression) พิมพ์ 1400014AE กด Enter
  3. คลิกขวาที่บรรทัดนั้น (จะเห็น je AntiCapture.1400014E6) → Assemble (หรือกด Space)
  4. พิมพ์ jmp 1400014E6 แทนที่ (ปลายทางเดิม แค่เปลี่ยนจาก conditional เป็น unconditional) → กด OK
  5. คลิกขวาที่หน้าต่าง CPU → Patches (หรือ Alt+P) → เลือก patch ที่เพิ่งทำ → Save File เพื่อเขียนกลับลงไฟล์จริง
ทางเลือก: hex editor

ถ้าไม่อยากใช้ x64dbg เปิดไฟล์ด้วย hex editor (เช่น HxD) แล้วกด Ctrl+G ไปที่ file offset 0xAAE (ไม่ใช่ VA) จะเห็น byte 74 36 — เปลี่ยนเป็น EB 36 แล้ว save

{

  } else {

จุดสำคัญ

ข้อความ MessageBox ต่างกัน แต่ ค่าที่ return เหมือนกันทุกกรณี — เป็นแค่ของหลอกล่อ ไม่ต้องสนใจว่า pack หรือไม่

4

ดูว่าทำไม key นี้ยังไม่ผ่าน — เปิดฟังก์ชัน drop_encrypted_file

จาก WinMain จะเห็นว่า key ที่ได้ถูกส่งต่อไปยัง drop_encrypted_file(key, ...) — เปิดฟังก์ชันนี้ดู:

for (i=0; i<16; i++) local_38[i] = key[i] ^ 0x1F;   // decode ทีละ byte

if (local_38[15]=='O' && local_38[14]=='T' &&
    local_38[13]=='U' && local_38[12]=='^') {
    // ผ่าน → โชว์ Answer + AES decrypt ต่อ
} else {
    MessageBoxA(...,"Detection Triggered!",...);
}

ถอดสมการ: byte ตำแหน่ง 12-15 (นับจาก 0) ของ key ต้อง decode ได้เป็น A J K P พอดี — แต่ "thisisnotpacked" มีแค่ 15 ตัวอักษร (ตำแหน่ง 12-14 = k,e,d) จึงไม่มีทางผ่านได้เลยจากโค้ดต้นฉบับ

5

หาตำแหน่ง 4 jump ที่ต้อง patch

ใน Listing panel ของ drop_encrypted_file ไล่หาบล็อกเปรียบเทียบ 4 ครั้งติดกัน (คลิกจากบรรทัด compare ใน decompile panel เพื่อกระโดดไปที่ assembly ตรงจุด):

InstructionBeforeAfterเหตุผล
JNZ (เช็ค byte[15]=='O')75 2190 90NOP ทิ้ง ไม่ให้กระโดดไป fail
JNZ (เช็ค byte[14]=='T')75 1690 90NOP ทิ้ง
JNZ (เช็ค byte[13]=='U')75 0B90 90NOP ทิ้ง
JZ (เช็ค byte[12]=='^')74 2DEB 2Dเปลี่ยนเป็น JMP ไม่มีเงื่อนไข → เข้า success เสมอ
ทำไม 4 จุด ไม่ใช่จุดเดียว

3 อันแรกเป็น JNZ ...fail_label — ถ้าไม่ patch แม้แต่อันเดียว โปรแกรมจะกระโดดไป fail ก่อนถึงจุดสุดท้าย เพราะงั้นต้อง NOP ทั้ง 3 อันก่อน แล้วค่อยเปลี่ยนอันสุดท้ายเป็น JMP

6

Patch ด้วย x64dbg (4 จุดรวด)

เปิด Anti_Packing_patched.exe (สำเนาของไฟล์ unpacked) ใน x64dbg แล้วทำซ้ำขั้นตอนนี้ 4 รอบ:

  1. Ctrl+G ไปที่ address ของแต่ละ jump (ดูจาก Ghidra Listing ของคุณเอง — เลขอาจขยับจาก cheat sheet เล็กน้อยถ้า compile ต่างเวอร์ชัน)
  2. 3 จุดแรก: คลิกขวา → Assemble → พิมพ์ nop กด OK แล้วเลื่อนไปบรรทัดถัดไปในกลุ่มเดียวกัน พิมพ์ nop อีกที (JNZ ใช้ 2 byte = nop 2 ครั้ง หรือเลือกช่วง 2 byte แล้ว assemble รวดเดียวก็ได้)
  3. จุดสุดท้าย (JZ): Assemble แล้วพิมพ์ jmp <ปลายทางเดิมที่เห็นในบรรทัด>
  4. Alt+P → Save File เมื่อ patch ครบ 4 จุด

Anti Temper

เป้าหมาย: Anti_Temper.exe

1

Triage ด้วย DIE

PE64
Compiler: MinGW (GCC 15.1.0)
2

วิเคราะห์ custom_anti_analysis_check

เปิดใน Ghidra → analyze → ดูฟังก์ชัน custom_anti_analysis_check:

GetModuleFileNameA(0, path, ...);       // เอา path ตัวเอง
fopen(path, "rb");
md5File(...);                            // คำนวณ MD5 ของไฟล์ตัวเอง
fopen("WELCOME_TO_THE_DARKNESS.txt","r"); // เปิดไฟล์ hash ที่ฝังไว้ในแล็บ
fread(...); hex_string_to_bytes(...);
if (memcmp(md5_คำนวณ, md5_จากไฟล์, 16) == 0) {
    return "PKJAA7A15A7AEF4A";           // "ผ่าน" self-check
} else {
    MessageBoxA(...,"i was hijacked, good people not doing this !",...);
    return "notme12345678912";
}

ไฟล์ WELCOME_TO_THE_DARKNESS.txt ที่แถมมาในชุดโจทย์ มีค่า MD5 ของไฟล์ Anti_Temper.exe ต้นฉบับ (ไม่ถูกแก้) ฝังไว้อยู่แล้ว — ถ้าไฟล์ยังไม่ถูกแก้เลย MD5 จะตรงกันเอง

3

ทำไม MD5 ผ่าน ก็ยังไม่พอ

เปิดฟังก์ชัน drop_encrypted_file — เป็น gate check แบบเดียวกับ Challenge 2 เป๊ะ (เช็คว่า key ที่ decode แล้ว ลงท้ายด้วย AJKP) แต่ "PKJAA7A15A7AEF4A" (key ที่ได้แม้ MD5 จะตรง) มีตัวอักษรตำแหน่ง 12-15 เป็น E,F,4,A — ไม่ใช่ A,J,K,P

สรุป

ต่อให้ไม่แก้ไฟล์เลยแม้แต่ byte เดียว (MD5 ตรง 100%) ก็ ไม่มีทางผ่าน gate check ท้ายสุดได้อยู่ดี — เท่ากับ self-integrity check ทั้งหมดเป็นเพียงฉากหน้า จุดที่ต้อง patch จริงคือ drop_encrypted_file ไม่ใช่ส่วนคำนวณ MD5

ทำไมห้าม patch MD5 โดยตรง

ถ้าไปพยายามแก้ให้ MD5 "ตรง" หลังจาก patch โค้ดอื่น จะวนลูปไม่จบ (แก้ไฟล์ → MD5 เปลี่ยน → ต้องแก้ hash ที่ฝังไว้ → แต่ hash มาจากไฟล์ .txt แยกต่างหาก ไม่ใช่ใน .exe) วิธีที่ถูกต้องคือ patch จุด compare ผลลัพธ์สุดท้าย ใน drop_encrypted_file แทน ให้ self-check ทั้งกระบวนก่อนหน้าไม่มีผลอะไรเลย

4

หาตำแหน่ง 4 jump ใน drop_encrypted_file

วิธีหาเหมือน Challenge 2 เป๊ะ — ไล่จาก decompile panel ไปยัง assembly ของบล็อก if (byte[15]=='O' && ...) จะเจอ 4 instruction ติดกัน (3 JNZ + 1 JZ)

InstructionBeforeAfter
JNZ (byte[15]=='O')75 2190 90
JNZ (byte[14]=='T')75 1690 90
JNZ (byte[13]=='U')75 0B90 90
JZ (byte[12]=='^')74 2DEB 2D

ถอดสมการหา key ที่ถูกต้อง

ต้องการ decode == "O+H" → ย้อนกลับ (XOR ด้วย 0x1F อีกที) หาค่า byte ต้นฉบับที่ต้องมี:

ตำแหน่งต้อง decode เป็นต้นฉบับต้องเป็น
DAT_140004000'O' (0x4F)'P' (0x50)
DAT_140004001'+' (0x2B)'4' (0x34)
DAT_140004002'H' (0x48)'W' (0x57)

สังเกตว่า byte ตัวที่ 3 ('W'=0x57) คือค่าที่ timing check ตั้งใจจะ set เวลาโปรแกรมรันเร็ว — ตรงกันพอดี ปัญหาจึงไม่ได้อยู่ที่ timing เลย

ตรวจ byte จริงในไฟล์ — เจอบั๊ก

เปิดไฟล์ด้วย hex editor ไปที่ตำแหน่ง DAT_140004000 (ดู VA จาก Ghidra แล้วแปลงเป็น file offset — ในไฟล์ชุดนี้ คือ 0x3600) จะเห็น:

offset 0x3600: 50 58 57 00
                P  X  W  \0
พบสาเหตุ

byte ตัวกลางเป็น 0x58 ('X') แทนที่จะเป็น 0x34 ('4') ตามที่ต้องการ — เป็น บั๊กที่ฝังอยู่ใน data ตรง ๆ ไม่เกี่ยวกับ timing check เลย ต่อให้รันเร็วแค่ไหน ก็ไม่มีทางได้ "O+H" ครบถูกต้อง เพราะ byte กลางผิดตั้งแต่ต้น
